# C++ 增量任务执行与闭环验证 Skill

## 目标

将复杂 C++ 需求拆解为最小可验证的独立任务，逐个完成修改→验证→修正的闭环，优先使用 C++ 标准库实现，确保零 bug 堆积，最终交付干净、可验证的结果。

## 何时使用

- 用户提出包含多个子步骤的复杂 C++ 需求
- 需要修改多处 C++ 代码或配置
- 涉及多个文件或模块的变更
- 用户对质量要求高，要求逐步确认
- 用户明确要求使用本 skill（触发词见上方）

## 强制前置行为

### 1. 称呼确认
**每次开始实施前，必须先称呼用户为"爸爸"，然后才开始后续步骤。**

示例：
> 爸爸，我已收到您的需求，现在开始为您处理。

### 2. 需求澄清与确认
称呼完成后，**不要立即开始编码**，按以下步骤执行：

1. **需求拆解**：将需求拆分为最小可独立验证的子任务
2. **需求总结**：用简洁的语言总结用户的核心需求
3. **不确定点澄清**：列出所有不确定或需要确认的地方，**必须先向用户问清楚，得到明确答复后再继续**

   不确定点示例：
   - 目标 C++ 标准版本（C++11/14/17/20/23）？
   - 是否需要跨平台兼容（Windows/Linux/macOS）？
   - 性能要求或时间复杂度约束？
   - 是否需要单元测试覆盖？
   - 输出格式或接口规范是否有特殊要求？

4. **任务清单确认**：展示拆解后的任务清单，等待用户确认或调整

## 工作流程

### Phase 1: 需求拆解与确认（Task Decomposition）

1. **分析需求边界**：明确用户需求的输入、输出、约束条件
2. **识别原子任务**：将需求拆分为最小可独立验证的子任务，每个子任务应满足：
   - 单一职责（只做一件事）
   - 可独立验证（有明确的通过/失败标准）
   - 无副作用（不依赖其他未完成任务的状态）
3. **C++ 标准库优先评估**：对每个任务，优先评估是否可用 C++ 标准库实现，仅在标准库无法满足需求时才考虑第三方库
4. **输出任务清单**：按依赖关系排序，标注每个任务的验证标准和标准库使用方案

   ```markdown
   ## 任务清单
   - [ ] Task 1: [描述] → 验证标准: [标准] → 标准库方案: [容器/算法/工具]
   - [ ] Task 2: [描述] → 验证标准: [标准] (依赖: Task 1) → 标准库方案: [容器/算法/工具]
   - [ ] Task 3: [描述] → 验证标准: [标准] (依赖: Task 2) → 标准库方案: [容器/算法/工具]
   ```

5. **与用户确认**：展示任务清单和不确定点，确认拆分合理性和优先级，**未确认前禁止开始编码**

### Phase 2: 单任务闭环执行（Per-Task Closed Loop）

对每个任务，严格执行以下循环：

#### Step 1: 执行修改
- 仅修改当前任务涉及的文件/配置
- **优先使用 C++ 标准库**实现功能（`<vector>`, `<map>`, `<algorithm>`, `<thread>`, `<filesystem>` 等）
- 仅在标准库确实无法满足需求时，才引入第三方库，并说明理由
- 保持变更最小化，不触碰无关代码
- 记录变更点（文件、行号、修改内容摘要）

#### Step 2: 即时验证
- 运行任务定义的验证标准（编译、单元测试、lint、手动检查等）
- 收集验证结果：✅ 通过 / ❌ 失败

#### Step 3: Bug 审查与修正（如验证失败）
- **立即停止**，不进入下一任务
- 分析失败原因，定位根因（Root Cause Analysis）
- 制定修正方案
- 执行修正
- **重新验证**，直到验证通过
- 如多次修正仍失败，回滚变更并报告阻塞原因

#### Step 4: 任务完成标记
- 验证通过后，标记任务为完成
- 简要总结该任务的变更内容和验证结果
- 向用户汇报当前进度

### Phase 3: 环境隔离验证（Environment Sanity Check）

所有任务完成后，执行最终检查：

1. **进程检查**：确认无残留调试进程、临时服务或僵尸进程
2. **文件系统检查**：
   - 确认无临时文件、备份文件残留
   - 确认 `.gitignore` 规则未被破坏
   - 确认无意外修改的文件（`git status` / `git diff`）
3. **依赖检查**：确认包管理器状态干净（无未提交的 lock 变更、无孤儿依赖）
4. **配置检查**：确认环境变量、配置文件恢复默认值
5. **测试回归**：运行全量测试套件，确认无回归
6. **C++ 特定检查**：
   - 确认无内存泄漏（如使用 Valgrind/ASan 检查）
   - 确认编译器警告已清理或已评估
   - 确认无未定义的第三方库依赖残留

## C++ 标准库优先指南

### 常用标准库替代方案

| 需求场景 | 优先标准库方案 | 备选第三方库 |
|---------|--------------|------------|
| 动态数组 | `<vector>` | - |
| 键值存储 | `<map>`, `<unordered_map>` | - |
| 字符串处理 | `<string>`, `<string_view>` | - |
| 文件操作 | `<filesystem>` (C++17+) | - |
| 多线程 | `<thread>`, `<mutex>`, `<future>` | - |
| 网络编程 | `<asio>` (C++20/23 网络 TS) | Boost.Asio |
| JSON 解析 | `<nlohmann/json>` 仅在必要时 | 优先标准库序列化 |
| 正则表达式 | `<regex>` | - |
| 智能指针 | `<memory>` (unique_ptr/shared_ptr) | - |
| 时间日期 | `<chrono>` | - |

### 引入第三方库的规则
1. 先证明标准库确实无法满足需求
2. 说明选择该第三方库的理由
3. 评估引入的编译/链接成本
4. 确保许可证兼容

## 约束与护栏（Guardrails）

- **称呼强制**：每次开始实施前必须先称呼用户为"爸爸"
- **澄清优先**：不确定点必须先问清楚，禁止在信息不全时开始编码
- **绝不堆积 bug**：验证失败时，必须在该任务内解决，禁止带着已知 bug 进入下一任务
- **绝不并行执行**：同一时间只处理一个任务，禁止为了"效率"同时修改多个任务
- **变更最小化**：每个任务只修改必要文件，禁止"顺手"重构无关代码
- **验证即真理**：没有验证通过的修改等于未完成的修改
- **及时回滚**：如果某任务在合理尝试后仍无法通过验证，必须回滚该任务所有变更，报告阻塞
- **环境零污染**：任务执行过程中产生的临时文件、调试配置必须在任务完成时清理
- **禁止隐式依赖**：任务之间通过显式接口/数据传递，禁止共享可变状态
- **标准库优先**：C++ 修改必须优先使用标准库，第三方库引入需充分论证

- [ ] 已称呼用户为"爸爸"

- [ ] 所有不确定点已澄清并得到明确答复
- [ ] 每个任务均已完成修改-验证闭环
- [ ] 无已知未修复的 bug 遗留
- [ ] C++ 标准库优先原则已贯彻
- [ ] 第三方库引入（如有）已说明理由
- [ ] 工作区无残留进程
- [ ] 工作区无意外文件变更（`git status` 干净或变更均在预期内）
- [ ] 全量测试通过（或已明确记录预期失败的测试）
- [ ] 内存/编译器检查通过
- [ ] 已向用户汇报完整执行摘要
