## 2. 串口通信协议（V2.0）

### 物理层
- 波特率：921600，92160 字节/秒
- 帧：一次完整可校验的最小有效单元
- EC → MiniPC：51 字节，帧头 `0x47 0x44` ("GD")
- MiniPC → EC：25 字节，帧头 `0x51 0x59` ("QY")

### 上行帧（EC→视觉）51 字节关键字段

| 偏移 | 字段 | 视觉用途 |
|:----:|------|---------|
| 2 | `frame_id` | 未用 |
| 3-14 | `real_Vel_x/y`, `real_Omega_z` | 底盘速度反馈 |
| 15-22 | `Chassis_Eular_Angle[0/1]` | 底盘Yaw/Pitch (rad) |
| 23-30 | `Omrga_Chassis[0/1]` | 云台Yaw/Pitch角速度 (rad/s) |
| **36** | **`gimbal_req_mode`** | **EC请求视觉模式：0x10=IDLE, 0x11=自瞄, 0x12=小符, 0x13=大符** |
| 37-48 | `Gimbal_Eular_Angle[0/1/2]` | 云台Yaw/Pitch/Roll (rad) |

### 下行帧（视觉→EC）25 字节

| 偏移 | 字段 | 编码方式 |
|:----:|------|---------|
| 2 | `gimbal_mode` | 0x00=DISABLE, 0x01=NO_FIRE, 0x02=FIRE |
| 3-6 | Yaw 目标角 | `uint_to_float(x, -π, π, 32)` |
| 7-10 | Pitch 目标角 | 同上 |
| 11-14 | 底盘 X 速度 | `uint_to_float(x, -1, 1, 32)` |
| 15-18 | 底盘 Y 速度 | 同上 |
| 19-22 | 底盘角速度 | 同上 |

**量化公式**（收发一致）：x = val / (2^32 - 1) × range + min

### ⚠️ 已发现的问题

1. **`gimbal_req_mode` 值不匹配**：EC 发 `0x11`，代码判断 `== 1`，模式永远 IDLE。已修正为 `== 0x11/0x12/0x13`。
2. **EC 端 Roll 组包 bug**：`MiniPC.c` 第 45-48 字节缺少低字节 `>>0`，高字节重复 `>>24`。
3. **`gimbal_mode`（下行）和 `gimbal_req_mode`（上行）是不同方向的不同字段，不要混淆取值。**

## 3. 导航与视觉的 ROS2 通信

```
视觉不依赖导航也能独立跑。导航只用于哨兵追人的速度补偿。

导航(Nav2) ──/cmd_vel(Twist)──→ Nav2Aim(视觉订阅) → gimbal.send(vx,vy,wz)
视觉(Aim2Nav) ──/ec2nav_chassis_state──→ 导航(nav_pub决策)
```

| 组件 | 方向 | 当前状态 |
|------|:--:|------|
| `Nav2Aim` | 订阅 `/cmd_vel` | QYG_sentry_debug 中被注释 |
| `Aim2Nav` | 发布 `/ec2nav_chassis_state` | 有 publisher 但**没有 spin** → 发不出去 |

建议：让视觉程序统一读写串口，把 EC 数据通过 ROS2 发布，导航侧只订阅即可。

## 4. ROS2 核心概念

### spin

`rclcpp::spin(node)` 是 ROS2 的事件循环。没有 spin：
- `publish()` 的消息堆积在缓冲区，不会到达网络
- 订阅回调永远不会被触发

### rclcpp

ROS2 的 C++ 客户端库，提供 `Node`、`Publisher`、`Subscription`、`spin` 等核心接口。

## 5. 自瞄核心算法

### 管线流程

```
相机读帧 → YOLO检测 → Solver(PnP解算) → Tracker(EKF跟踪) → Planner(MPC) → 输出指令
```

### Solver：空间维度的位姿解算

- 输入：图像上 4 个装甲板角点
- 方法：PnP (Perspective-n-Point)
- 输出：装甲板在**世界坐标系**下的 3D 位置 `(x, y, z)` 和朝向 `yaw`
- 依赖：相机内参 + 手眼标定外参 + **云台当前姿态** `R_gimbal2world`

### Tracker：时间维度的状态估计

- 输入：Solver 解算出的 Armor 列表 + 时间戳
- 方法：扩展卡尔曼滤波 (EKF) + 状态机
- 输出：`Target`（位置、速度、角速度的滤波估计）
- 状态机：`lost → detecting → tracking → temp_lost → lost`
- 关键：通过 `dt`（两帧时间间隔）做状态预测

### 时间戳对齐（关键设计）

```
camera.read() 返回的是"收到图像"的时刻 t
真实曝光时刻 ≈ t - 1ms（补偿 USB/GigE 传输延迟）

gimbal.euler(t - 1ms)：取曝光时刻的云台姿态（线性插值）
solver.set_R_gimbal2world(q)：用曝光时刻的姿态做 PnP 坐标变换
tracker.track(armors, t)：用两帧间隔 dt 做 EKF 预测
```

### IMU 插值原理

```cpp
k = (t - t_a) / (t_b - t_a)  // 目标时刻落在 [t_a, t_b] 的比例
euler_c = euler_a + k * (euler_b - euler_a)  // 线性插值
```

**为什么线性插值可行**：IMU 采样间隔仅为 ~1ms，在 1ms 内云台角度变化极小（10rad/s × 0.001s = 0.01rad < 0.6°），线性近似的误差远小于 PnP 解算本身误差（1°~3°）。

### MPC vs 传统 PID

| | 传统 PID | MPC（本项目） |
|:--|:--|:--|
| 决策方式 | 当前偏差 → 控制量 | 预测未来 1 秒轨迹 → 优化控制序列 |
| 延迟处理 | 被动追 | 主动预测补偿 |
| 开火决策 | 单独判断 | 融入轨迹优化 |

MPC 使用 `tinympc`（轻量 ADMM 求解器），yaw 和 pitch 通道独立优化，预测窗口 100 步（1 秒）。
