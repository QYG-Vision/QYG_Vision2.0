## 1. Nav2Aim — 导航→视觉的数据通道

### 1.1 接收的数据

`Nav2Aim` 订阅 ROS2 话题 `/cmd_vel`，消息类型是 `geometry_msgs::msg::Twist`：

| 字段 | 含义 | 视觉用到？ |
|------|------|:--:|
| `linear.x` | 底盘 X 方向线速度（前后） | ✅ |
| `linear.y` | 底盘 Y 方向线速度（左右） | ✅ |
| `linear.z` | 不建议使用 | ❌ |
| `angular.x` | 不建议使用 | ❌ |
| `angular.y` | 不建议使用 | ❌ |
| `angular.z` | 底盘 Z 轴角速度（原地转向） | ✅ |

**即 `vx`, `vy`, `wz` 三个速度值。**

### 1.2 消息类型是"命令"而非"状态"

`/cmd_vel` 中的 "cmd" = command（命令），是导航**期望**底盘达到的**目标速度**，不是底盘实际速度。底盘实际速度由 MCU 通过编码器和陀螺仪实测后，写入 51 字节 GD 帧中的 `actual_vx/vy/wz` 反馈回来。

### 1.3 完整函数调用链

```
Nav2 发布                       Nav2Aim 接收                      视觉主线程读取
┌──────────┐         ┌─────────────────────────┐        ┌──────────────────────┐
│ publish() │ ─ROS2─→ │ cmd_vel_callback(msg)   │        │ get_latest_state()   │
│ cmd.      │         │   mutex_.lock()          │        │   mutex_.lock()      │
│ linear.x  │         │   latest_state_ = *msg;  │ ─副本─→│   return latest_     │
│ linear.y  │         │   mutex_.unlock()        │        │   state_;            │
│ angular.z │         └─────────────────────────┘        │   mutex_.unlock()    │
└──────────┘                                              └──────────────────────┘
  导航进程                                                    视觉进程（同一台 NUC）
```

**回调函数** `cmd_vel_callback()` 由 ROS2 内部线程**自动调用**，不需要你的代码主动触发。

| 阶段 | 函数 | 输入 | 输出 |
|------|------|------|------|
| 发布 | Nav2 内部 `publish()` | 速度值 | ROS2 网络 |
| 接收 | `cmd_vel_callback(msg)` | 消息指针 | 存入 `latest_state_` |
| 读取 | `get_latest_state()` | 无 | Twist 结构体副本 |
| 使用 | `gimbal.send(...)` | 速度值 | 串口发到 MCU |

### 1.4 三句关键代码的当前状态


## 2. 视觉端用导航速度做计算吗？

**不做任何计算，直接透传给 MCU！**

`Planner::plan()` 的接口签名证明了这一点：

```cpp
Plan plan(Target target, double bullet_speed);
//        ↑                ↑
//     只需要目标状态     只需要弹速
//     不接收底盘速度！
```

在"真正有导航接入"的版本（`QYG_sentry_debug copy.cpp`）中：

```cpp
auto cmd_vel = nav2aim.get_latest_state();   // {vx, vy, wz}

gimbal.send(
    plan.control, plan.fire,                 // 视觉的瞄准+开火决策
    plan.yaw, plan.pitch,                     // 视觉 MPC 算的云台角度
    cmd_vel.linear.x,                         // ← vx 原样塞进去
    cmd_vel.linear.y,                         // ← vy 原样塞进去
    cmd_vel.angular.z                         // ← wz 原样塞进去
);
```

视觉拿到导航速度的**唯一用途**：原样打包进 25 字节 QY 帧，发串口给 MCU。视觉程序是"快递员"，不是"消费者"。

## 3. 为什么 MPC 不需要底盘速度？

### 3.1 分工不同

| 视觉 MPC | MCU（下位机） |
|:--------|:------------|
| 回答："云台应该指向哪个角度" | 回答："电机应该转多少圈才能指到那个角度" |
| 输入：目标世界坐标 + 弹速 | 输入：MPC 的目标角度 + 陀螺仪实测当前角度 |
| 频率：~30Hz（相机帧率） | 频率：~1000Hz（陀螺仪采样率） |

MCU 自带 1kHz 的陀螺仪反馈闭环——底盘向左转 2°，陀螺仪立即检测到，MCU 自动在电机指令上补偿 +2°。视觉完全不需要知道底盘在干嘛。

### 3.2 EKF 已隔离底盘运动

Tracker 中的扩展卡尔曼滤波把目标状态估计在**世界坐标系**下。底盘平移或旋转不影响目标在世界坐标系中的位置，所以 MPC 不需要底盘速度输入。

### 3.3 MCU 每帧已经发来真实底盘数据

51 字节 GD 上行帧中的字段：

| 字段 | 含义 | 视觉当前用法 |
|------|------|:--:|
| `actual_vx/vy/wz` | 编码器实测底盘速度 | ❌ 存了但没用 |
| `odom_x` | 里程计累计距离 | ❌ 存了但没用 |
| `imu_yaw/pitch` | 底盘姿态角 | ✅ 用于坐标变换 |
| `vyaw/vpitch/vroll` | 云台欧拉角 | ✅ 用于 gimbal.euler() 插值 |

**视觉只用了云台姿态角来做坐标变换和 PnP 解算**，底盘速度数据有但不需要。

## 4. 导航为什么需要视觉的数据？

`nav_pub` 节点订阅 `/ec2nav_chassis_state`，根据视觉的工作模式决定底盘去哪：

```cpp
// nav_pub/state_pub.hpp 节点行为注释
/// 1. 订阅 /ec2nav_chassis_state
/// 3. current_mode == 0 时忽略（空闲→回家）
/// 4. current_mode == 1 时发送占点目标（自瞄→前压）
/// 5. current_mode == 2 时发送基地目标
```

| 导航自己知道的 | 导航不知道的（需要视觉告诉） |
|:------------|:--------------------------|
| ✅ 地图 | ❌ 视野内有没有敌人？ |
| ✅ 自己的位置 | ❌ 现在是 IDLE 还是自瞄？ |
| ✅ 障碍物在哪 | ❌ 该去占点还是回家？ |

**没有视觉→导航这条通路，导航就是个瞎子。**

### 当前的通路状态

| 方向 | 话题 | 状态 |
|:--:|------|:--:|
| 导航→视觉 | `/cmd_vel` | ⏸️ 被注释掉（调试用模拟速度替代） |
| 视觉→导航 | `/ec2nav_chassis_state` | ❌ Aim2Nav 有 publisher 但没 spin → 发不出去 |

## 5. 双向 ROS2 通信的必要性（完整代码解析）

### 5.1 通路一：导航→视觉 (`/cmd_vel`)

导航系统规划底盘路径，通过 `/cmd_vel` 下发速度，视觉打包给 MCU 执行：

```cpp
// ============ 导航侧：发布 /cmd_vel ============
geometry_msgs::msg::Twist cmd;
cmd.linear.x  = 0.3;    // 向前 0.3 m/s
cmd.linear.y  = -0.5;   // 向左 0.5 m/s
cmd.angular.z = 0.1;    // 逆时针转 0.1 rad/s
nav_publisher->publish(cmd);

// ============ 视觉侧：订阅 /cmd_vel ============
// nav2aim.cpp — 自动回调，存入对象内部成员变量
void Nav2Aim::cmd_vel_callback(const Twist::SharedPtr msg) {
    std::lock_guard<std::mutex> lock(mutex_);
    latest_state_ = *msg;    // {0.3, -0.5, 0.1} 写入对象内部
}

// QYG_sentry_debug copy.cpp — 拿速度，原样打包发给 MCU
auto cmd_vel = nav2aim.get_latest_state();   // {0.3, -0.5, 0.1}
gimbal.send(
    plan.control, plan.fire,                 // 视觉的瞄准+开火决策
    plan.yaw, plan.pitch,                     // 视觉 MPC 云台角度
    cmd_vel.linear.x, cmd_vel.linear.y,       // ← 导航速度透传给 MCU
    cmd_vel.angular.z
);
```

**如果这条断了**：MCU 收到的底盘速度永远是 0，哨兵原地不动。

### 5.2 通路二：视觉→导航 (`/ec2nav_chassis_state`)

视觉需要告诉导航当前在干什么，导航据此决定去哪：

```cpp
// ============ 视觉侧：发布 /ec2nav_chassis_state ============
// aim2nav.cpp — publish() 把 EC 模式发到 ROS2
void Aim2Nav::publish(const GimbalState & state) {
    std_msgs::msg::UInt8MultiArray msg;
    msg.data = {
        state.current_mode,    // [0] 当前模式
        state.mode             // [1] EC 请求的视觉模式
    };
    state_pub_->publish(msg);   // ⚠️ 需要 spin 才能真正发出去！
}

// ============ 导航侧：订阅 /ec2nav_chassis_state ============
void NavPubNode::chassis_state_callback(const UInt8MultiArray::SharedPtr msg) {
    uint8_t current_mode = msg->data[0];

    if (current_mode == 0) {
        send_goal_for_mode(0);  // IDLE → 回家守路口 (0, 0)
    } else if (current_mode == 1) {
        send_goal_for_mode(1);  // AUTO_AIM → 去占点 (1.0, 0)
    }
}
```

**如果这条断了**：导航永远不知道视觉在干什么，只能原地发呆。

### 5.3 完整时间轴示例

```
t₀: 视觉检测到敌人
    → 发布 current_mode=1 到 /ec2nav_chassis_state
    → 导航收到："哦，自瞄了！" → 下发导航目标：去占点
    → 导航开始规划路径 → 发布 /cmd_vel = {0.3, -0.5, 0.1}

t₁: 视觉收到 /cmd_vel
    → 打包进 QY 帧 → 串口发给 MCU
    → MCU 执行：云台指向敌人 + 底盘向右前方行驶
    → MCU 通过 51 字节 GD 帧反馈：actual_vx=0.28, imu_yaw=15°

t₂: 敌人被打掉
    → 视觉发布 current_mode=0
    → 导航收到："停火，回家" → 更新 /cmd_vel 目标
```

### 5.4 为什么必须双向

| 方向 | 话题 | 传递什么 | 最终谁用 | 断了会怎样 |
|:--:|------|------|------|------|
| 导航→视觉 | `/cmd_vel` | 底盘目标速度 | MCU | 底盘永远不动 |
| 视觉→导航 | `/ec2nav_chassis_state` | 当前工作模式 | 导航决策 | 不知道去哪 |

> **导航是底盘的大脑，视觉是云台的眼睛。大脑需要眼睛告诉它"看到敌人了吗"，眼睛需要大脑告诉它"底盘要怎么配合"。两者都断 → 系统瘫痪。**

## 6. Aim2Nav 当前不工作的原因（spin 问题）

`Aim2Nav` 创建了 publisher 但没有调用 `rclcpp::spin(node_)`，导致 `publish()` 的消息堆积在 ROS2 内部缓冲区，从未到达 DDS 网络。

```cpp
Aim2Nav::Aim2Nav() {
    node_ = new Node("aim2nav");
    state_pub_ = node_->create_publisher("/ec2nav_chassis_state", 10);
    // 没有 spin！消息发不出去！
}
```

**修复方向**：类比 `Nav2Aim` 用 `start()` 启动独立 spin 线程的做法。

```
                    同一台运算设备（上位机 NUC）
┌──────────────────────────────────────────────────────────┐
│                                                          │
│  雷达(LiDAR) → 导航系统(Nav2)                             │
│                    │                                     │
│                    │ ROS2 /cmd_vel (Twist)                │
│                    ▼                                     │
│  相机(HIK) ──→ 视觉系统(自瞄算法)                          │
│   │                │                                     │
│   │           MPC 结果(yaw,pitch)                         │
│   │                +                                     │
│   │           导航速度透传                                 │
│   │                │                                     │
│   │          串口 (921600)                                │
│   │          25 字节 QY 帧                                │
│   │                │                                     │
│   └────────────────┤                                     │
│                    ▼                                     │
│  视觉 → 导航 ROS2  /ec2nav_chassis_state (UInt8MultiArray) │
│  Aim2Nav::publish()   ⚠️ 当前没 spin，发不出去            │
└──────────────────────────────────────────────────────────┘
                     │
                     ▼
           下位机 MCU (STM32F427)
           接收 QY 帧：解析 yaw/pitch/vx/vy/wz
           发送 GD 帧：51 字节全部传感器数据
```

## 8. 核心结论

1. **`Nav2Aim` 收到的 `/cmd_vel`** 是底盘目标速度 `vx, vy, wz`，视觉不对其做任何计算，直接透传给 MCU
2. **`Planner(MPC)` 不需要底盘速度** — 它只需要目标世界坐标和弹速，MCU 自己用 1kHz 陀螺仪闭环处理底盘扰动
3. **MCU 每帧 51 字节 GD 帧** 已包含编码器实测的底盘速度，视觉当前没有使用这些字段
4. **`Aim2Nav` 当前是死的** — 有 publisher 没 spin，导航收不到视觉模式，无法决策
5. **双向 ROS2 缺一不可** — cmd_vel 驱动底盘，ec2nav_chassis_state 告诉导航当前状态
